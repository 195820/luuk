# 媒体加载效率提升与卡顿治理实施方案（v2，已纳入 2026-09-18 审核修正）

> v2 变更摘要：① 缩略图通道由「IPC 批量二进制 + blob URL」改为「稳定 media:// URL」（审核 Critical#1/#2/#3/#10 一并消解）；② token 确定性哈希从 P2 前移为 P0 前置；③ 流式响应补 `stream:true` 特权并覆盖 Range 分支；④ 背压弃用不可达的 memoryMonitor；⑤ Lightbox 渐进加载改双 img 图层方案；⑥ 全部引用行号按当前代码修正；⑦ 确定性 token 由裸 `sha1` 改为 `HMAC-SHA1(sessionSecret, 标识)`（密钥每次启动随机）以保留不可预测性（审核 Warning#1）；⑧ 明确「无缩略图」分支的 falsy 契约（返回 `''`、不注册 token）与 200 响应的 `Content-Length`（审核 Warning#2）。

### 五大瓶颈（断言均经代码核实）
1. **缩略图数据链路低效**：`image-service.ts` L610（DB 命中）、L658-659（生成后）、L700-701（批量）、L798/L808（视频）共 5 处以 `data:image/webp;base64` 字符串回传（+33% 体积、主进程同步序列化大字符串）；`ImageGridItem.tsx` L112-113 每卡片一次 IPC（n+1）；批量接口 `getThumbnails`（imageStore.ts L93/L431 声明）**全仓零调用点**。另有休眠高危接口 `loadFullImage`（library-handlers.ts L410-421）整文件 base64 直传，当前无调用方。
2. **media:// 响应非流式、无缓存头、token 不稳定（三重叠加）**：`main.ts` L122 完整响应 `readFile` 整包读内存；L100-107 Range 分支 `Buffer.alloc(length)` 同样整块分配（`bytes=0-` 时即整文件）；L111-116/L124-128 全部响应缺 `Cache-Control/ETag`；且 `media-registry.ts` L50-55 每次 `registerMediaUrl` 生成新随机 token → **URL 每次变化，即便加了缓存头 Chromium 也永远 miss**。L130-131 任何异常折叠为 400，不利排障。
3. **瀑布流无视口窗口化**：`MasonryGrid.tsx` L289-333 双层 `map` 全量渲染，`columnTops` 仅用于 translateY 定位未做窗口过滤。影响范围限定：常规浏览条目被 limit 100 封顶（imageStore.ts L357）且普通库/收藏网格未传 `onLoadMore`（App.tsx L1306-1317），**仅搜索瀑布流（App.tsx L1276-1289）分页累积后 DOM 线性膨胀**——修复优先级因此从"高"调整为"中"，但仍需做（搜索大结果集是真实场景）。
4. **生成任务与 UI 抢资源**：全仓无 `sharp.concurrency()` 调用（实测默认并发 16，吃满全核）；视频缩略图两处人工等待：thumbnailer.ts L404-405（ffmpeg close 后 300ms，为 Windows 句柄/杀软兜底）与 L419-420/L424（"等待 sharp 释放句柄"200ms，真实后果是 rmSync 抛错被 L421/L425 的 try/catch 吞掉 → **`tmpdir/luuk-thumb-*` 静默泄漏**）；scanner.ts L135 BATCH_SIZE=10 批间无让渡；database.ts L1531-1535 `saveThumbnail` 单条 run 无事务；主连接未配置 WAL（database.ts L143 仅 foreign_keys）。
5. **Lightbox 原图直出**：App.tsx L783-789 `loadMedia` 仅取原图 media:// URL，ImageLightbox.tsx L292 直接渲染；几千万像素写真浏览器解码（~48MB RGBA/张）造成切换白屏。已有 `generatePreview(1200)`（thumbnailer.ts L165）**全仓无调用者**。

## 二、实施步骤

### P0-1 缩略图改走稳定 media:// URL 通道（核心方案，替代 v1 的 IPC 批量+blob）
**技术决策依据**（对比 v1 方案）：URL 通道让图片字节完全绕过渲染进程主线程 JS（无 IPC 序列化、无 blob→revoke 生命周期管理、无 Map/TypedArray 类型问题），n+1 IPC 变为浏览器网络栈自动并发 + HTTP 缓存，且**渲染进程近零改动**——`getThumbnail` 返回值从 data URL 字符串换成 `media://` URL 字符串，所有调用点（ImageGridItem L113、FolderTree L381、RecentHistory L17）赋值目标本来就是 `img.src`。

- `src/main/services/media-registry.ts`：
  - **token 改为确定性 HMAC 哈希（非裸哈希）**：`token = hmac_sha1(sessionSecret, 资源标识).slice(0,32)`（hex，兼容浏览器 authority 小写化）。`sessionSecret` 为**进程级密钥，每次 app 启动用 `crypto.randomBytes(32)` 随机生成**（存于 media-registry.ts 模块作用域常量）。这样既保留*同会话内确定性*（同一资源反复注册得到同一 URL，命中缓存），又保留原随机 token 的**不可预测性**——外部无法仅凭路径+mtime 离线推算 token，能力 URL 安全模型不被削弱（审核 Warning#1：裸 `sha1(资源标识)` 可预测，与 P2-1「按需重建」组合会导致库内文件被寻址）。资源标识：文件类=`absolutePath|mtimeMs`；缩略图类=`thumb|libraryId|imageId|size|generated_at`。
  - registry 条目扩展 `kind` 维度：`{ kind:'file', filePath }` 或 `{ kind:'thumb', libraryId, imageId, size }`；保留 1h TTL/10000 容量兜底，但确定性 token 使淘汰后重建得到同一 URL，不破坏缓存。
  - `registerMediaUrl` 改双参数（kind+标识），新增 `resolveMediaEntry` 返回条目对象。
- `src/main/services/image-service.ts`：
  - `getThumbnail/getThumbnails` 内部逻辑不变（LRU→DB→实时生成），**出口改为返回 `media://token` URL 字符串**；LRU 缓存值统一存**原始 Uint8Array**（修正 cache.ts L38-42 `entrySize` 按类型计算：`typeof v==='string'? v.length*0.75 : v.byteLength`，函数签名扩为 `string | Uint8Array`），彻底消除字符串/二进制混装同一 key（审核 Critical#1）。
  - 新增 `getThumbnailBytes(libraryId, imageId, size): Uint8Array | null` 供协议层调用（命中 LRU→DB→生成，逻辑复用现有 ①②③ 分支）。
  - **保留「无缩略图」的 falsy 契约（审核 Warning#2）**：缺失图片元数据（现 L620）、音频（L637）、`.avi/.mkv`（L642）等无缩略图分支，改走 URL 通道后**仍返回空字符串 `''`、且不调用 `registerMediaUrl` 注册任何 token**；对应 `getThumbnailBytes` 返回 `null`，协议层据此回 404。渲染层 `ImageGridItem.tsx` L115 `if (thumbnail)` 的占位/错误态判定依赖此契约，禁止用「指向不存在字节的 token」替代空串，否则会渲染坏图并发起无效协议请求。
- `electron/main.ts` `registerMediaProtocol`：
  - 协议处理增加 thumb 分支：`kind:'thumb'` 时从 `getThumbnailBytes` 取 WebP 字节，响应头 `Content-Type: image/webp` + `Cache-Control: public, max-age=604800, immutable`（URL 含版本哈希，immutable 安全）。
  - 沿用现有库目录白名单校验（thumb 资源天然在库内，按 libraryId 校验）。
- `src/main/ipc/library-handlers.ts`：`getThumbnail/getThumbnails` handler 返回 URL；`getThumbnails` 批量接口保留作为**预热用途**（渲染层滚动前调用一次，让主进程把 DB/生成做完，后续 img 请求全部直接命中）；**删除 `loadFullImage` handler 及 preload/global.d.ts 对应声明**（L410-421，休眠高危接口，趁无调用方下线）；同时从 `library-handlers.ts` L721-724 的 IPC 通道白名单数组中移除 `'loadFullImage'`（否则残留死条目）。
- `electron/preload.ts`：同步签名（返回值仍是 string，实际零改动）。
- 渲染层：仅加 `decoding="async"`（原 P2 项前移，一行改动零风险）。
- 依赖：无前置。**P0-2 的缓存收益依赖本项的 token 确定性哈希，必须先做或同批做**。

### P0-2 media:// 流式响应 + HTTP 缓存（原 v1 P0-2，修正三处）
- `electron/main.ts`：
  - **privileges 补 `stream: true`**（L31-41 当前缺失；Electron 文档明确 `<video>/<audio>` 对流协议默认按缓冲处理，不加有 seek 回归风险）。
  - **200 完整响应与 206 Range 分支统一**改为 `fs.createReadStream(path,{start,end})` → `stream/promises` + `Readable.toWeb()` 包 `ReadableStream`，删除 L122 `readFile` 整包与 L100 `Buffer.alloc(length)` 整块（`bytes=0-` 场景是主要内存峰值来源）；206 保留 `Content-Range/Content-Length/Accept-Ranges`；⚠️ **200 完整响应也须手动带 `Content-Length: String(stat.size)`**——`Readable.toWeb()` 不会自动补该头，缺失会导致部分 `<video>/<audio>` 缓冲与进度条退化。另：现有 Range 正则 `bytes=(\d+)-(\d*)`（L86）不覆盖 suffix 形式 `bytes=-N`，流式重构时一并支持（P2-1 预取用的是闭合区间，故非阻塞）。
  - 文件类响应加 `ETag`（sha1 of mtimeMs+size）与 `Cache-Control: max-age=86400`，处理 `If-None-Match` → 304。⚠️ 缓存实际命中率依赖 P0-1 的稳定 token（前置条件），上线前用 DevTools Network 验证 `media://` 请求出现 "(memory cache)"，不命中则退化为仅依赖主进程 LRU，不得阻塞发布。
  - L130 的 catch 拆分为 404（文件消失）/500（IO 错误），附日志。
- 依赖：token 稳定性部分依赖 P0-1；流式化本身独立可并行。

### P1-2 后台生成任务限流与泄漏治理（弃用 memoryMonitor 背压）
- `src/main/services/thumbnailer.ts`：
  - 模块入口 `sharp.concurrency(Math.max(1, os.availableParallelism() - 2))`。
  - **两处 sleep 分开处理（语义不同）**：
    - L404-405（ffmpeg 退出后）：改为轮询 `existsSync` + 连续两次 `stat.size` 稳定检测，间隔 50ms、**上限放宽至 2s**（v1 的 250ms 上限短于原 300ms，可能让 L407 存在性检查更早失败，已修正）。
    - L419-420（sharp 句柄）：不在成功路径等待，改为对 `fs.rmSync` 做 5×100ms 重试，仍失败则 `logger.warn` 记录；并注册 app `before-quit` 钩子全量清理 `tmpdir/luuk-thumb-*`（治理既有静默泄漏）。
  - 全局 ffmpeg 并发信号量 ≤ 2。
- `src/main/services/scanner.ts` `preGenerateThumbnails`：
  - BATCH_SIZE 从 10 改为 `Math.max(2, Math.floor(os.availableParallelism()/4))`。
  - **弃用 `memoryMonitor.isYellowOrAbove()` 背压**（审核 Critical#5：唯一实例是 PluginManager 私有字段且 `plugins.enabled` 默认 false 时 `start()` 永不执行 → 判断恒 false 静默失效；其阈值聚合全进程 RSS 300/400MB，Electron 多进程常态越线 → 一旦接通反而恒节流）。改为自足闸门：每批结束 `setImmediate` 让渡 + 实时读 `process.memoryUsage().rss`（仅主进程）阈值 ≥1.2GB 时暂停 200ms。
- `src/main/services/database.ts` + scanner：
  - 批量 `saveThumbnail` 用 `db.transaction` 包裹。⚠️ 约束：better-sqlite3 事务函数必须同步 → scanner 需"异步生成攒结果数组 → 同步一次性提交"两段式；事务按 libraryId 分组（this.db 是按库实例）。
  - 另立小任务评估 `journal_mode = WAL`（当前未配置，回滚日志模式下批量写 fsync 开销大；注意存量库文件兼容与退出 checkpoint）。
- 依赖：无前置，可与 P1-1 并行。

- 依赖：P0-1。

- `useAdjacentPreload.ts`：扩到视频首 1MB 预热（`fetch(mediaUrl, { headers:{ Range:'bytes=0-1048575' }})` 丢弃响应体，预热 OS 文件缓存与协议路径）；滚动方向感知的 ±3 预取。

## 四、风险与缓解
| 风险 | 缓解 |
|---|---|
| 协议层缩略图请求排队（浏览器对单 origin 并发有限）致首屏大量图片变慢 | 实测 protocol.handle 并发上限；必要时保留批量预热接口做 DB→生成前置填充（P0-1 已设计） |
| Chromium 对自定义 standard 协议是否真走磁盘/内存缓存无官方保证 | 上线前实测；不命中则接受"仅主进程 LRU"降级，收益仍成立（省 IPC/base64/渲染主线程） |
| 确定性 token 依赖 mtime，时间戳精度/回拨致 URL 抖动 | 用 `mtimeMs` 全精度 + `generated_at`（thumb 用 DB 列）；文件类另加 size 双因子 |
| 删除 loadFullImage 致未知调用方断裂 | 全仓 Grep 已确认渲染侧零调用；预加载白名单同步删除后跑全量回归 |
| stream:true 改变 video/audio 缓冲语义引发新行为差异 | 视频专项手工回归（seek/时长/快进）；异常则仅缩略图走流式、文件类保持整包 |
| preview 交叉淡入与 YARL zoom 层冲突 | 双 img 放在 YARL slide 容器外层做背景层，不侵入其 DOM |
| Windows 句柄占用（轮询替代 sleep 后） | 轮询上限 2s + 失败回退旧 300ms 固定等待；rmSync 重试 + quit 清理兜底 |
| WAL 模式与存量 .ivlib 兼容 | 独立任务、独立测试，不与 P1-2 捆绑上线 |

## 五、Rejected Alternatives
1. **缩略图改磁盘文件缓存**：SQLite BLOB 官方基准更快且更省空间，digiKam 同为分级 db；迁移收益为负。
2. **本地 HTTP 服务器供给媒体**：端口冲突、localhost 安全面扩大；`protocol.handle` + 手写 Range + 缓存头即可等效。
3. **全量 DeepZoom 瓦片金字塔**：仅对 >10000px 超大图有意义，当前写真分辨率下过度工程；P1-3 preview 渐进已覆盖体验痛点。
4. ~~缩略图走自定义协议 URL~~（v1 否决项，**v2 推翻并采纳为本方案 P0-1 主路径**）：v1 理由是"改造面大于 IPC 批量"，经 token 确定性哈希设计后该理由不成立——URL 通道在缓存、渲染主线程占用、改造面三个维度均优于 IPC+blob，且 blob URL 本就不进 Chromium HTTP 缓存（v1 对 blob 缓存能力的表述有误，一并更正）。
5. **IPC 批量返回 `Map<id, Uint8Array>`**（v1 方案）：Electron IPC/contextBridge 不保留 Map 原型方法（library-handlers.ts L291 既有注释证实），且 TypedArray 需穿透 isolated world；即便改用 Record 也只是次优解——被 URL 通道取代。
6. **P2-2 utilityProcess 全量迁移直接上**：改动进程模型，先以 P1-2 限流+事务验证数据，不达标再迁。
