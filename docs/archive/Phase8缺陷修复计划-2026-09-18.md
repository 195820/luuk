# Phase 8 缺陷修复计划（基于代码审查 2026-09-18，2026-09-19 依据审核意见修订）

## 概述
审查发现 Phase 8 骨架质量高但"端到端可用"不成立：批处理主链路未真正处理文件却报成功、upscale 对常规高清图必打爆 Worker 触发需重启的熔断、内存水位线口径漂移使 AI 执行门大概率恒拒；另有权限绕守卫、并发上下文串位、崩溃/重启后不可自愈等系统性隐患。本计划按优先级分五个里程碑修复，每个里程碑合入前跑 `tsc --noEmit` + `vitest run`（现 323 用例须保持全绿），全部完成后以 `npm run build:dir` 作为出口条件。

> **2026-09-19 修订说明**：二次审核对原计划提出 3 项 Critical（C1 P1-5 范围低估 / C2 P1-9 缺前置依赖 / C3 P1-11 回滚漏项）与 4 项 Warning（W1 P0-3 RSS 路径未定 / W2 P1-7 幂等去重过度设计 / W3 行号偏差 / W4 P0-2 预算未分解）。以下条目已据此修订，标注「[修订]」处为变更点。

审查报告以 P0-1…P2-19 编号随本计划内联（未单独落档 code-review 文件）；整改结果见 CHANGELOG 与 roadmap 第八轮。

## M1 · 主路径可用性（P0，最高优先）

### P0-1 批处理作业链闭合（当前假成功）
- `plugin-manager.ts registerOpHandlers()`（L210-224）：handler 内用现成的 `getImageService().getImagePath(item.libraryId, item.imageId)`（返回 `join(rootPath, relative_path)` 绝对路径）解析出路径，改传 `input: { paths:[abs], libraryId: item.libraryId, imageId: item.imageId }`，与交互式 `pluginsExecute` 的输入形态统一。`imageId` 为 null（如库级 op）时保留 `{ libraryId, item }` 并在插件侧显式支持。
- `skipped` 语义：内置插件入口返回 `skipped:true` 时，handler 抛错使 job_item 落 `failed`，杜绝"零工作却 done"。
- 渲染层接线：`ImageGrid.handleMenuAction` 增加"后台批处理"入口，多选量 > 阈值（如 20）时改走 `window.electronAPI.jobsEnqueue('ai.'+op, payload, { items:[{libraryId,imageId}] })`；交互式单项仍走 `pluginsExecute`。（`jobsEnqueue` 目前仅 preload/类型声明，无调用方。）
- **[修订·S1] 后台批处理用户感知**：触发 `jobsEnqueue` 后经 toast/imageStore 提示"已加入后台队列，可在进度面板查看"，并显式将 `JobProgressBar` 切为可见；避免 >20 张时菜单点击"什么都没发生"。
- 修正 CHANGELOG「批处理链闭合 / JobProgressBar 接线」表述，使其与实际交付一致。

### P0-2 upscale 输出像素预算守卫（防 OOM 熔断）
- `builtins/upscale/index.ts`（分配 `dst` 前，L128）：计算 `outW*outH`，超过 `MAX_OUT_PIXELS=40_000_000`（≈160MB RGBA）时抛可展示错误「输出过大(WxH)，请改用 2x 或先缩放」，避免 `new Uint8Array` + `encode` 复制打爆 utilityProcess → `MAX_CRASHES` 熔断。
- **[修订·W4] 预算分解**：单次峰值 ≈ `dst`(N·4) + `image.encode` 入口 `Buffer.from(data)` 复制(N·4) + PNG 输出(~0.4·N·4)，N=输出像素数。40M 像素峰值 ≈ 380MB，对齐 R7 实测 500MB 红线仅余 ~25%。
- **[修订·W4] 逐带（band）流式写盘——经实施调研降级为后续项**：upscale 当前走 `edit.write` 非破坏性编辑链（`sdk.image.encode(dst)` → 单个 PNG buffer → `edit.write({outputBuffer})`）。真正逐带写盘需改造 SDK 契约（`edit.write` 现仅接受完整 buffer）+ 将 sharp PNG 全图编码换为渐进式写盘器，跨 plugin-sdk-host/edits-service/worker-sdk/types 四处大改，属“允许更大图”的增强而非“防熳断”缺陷。**本里程碑以“预算守卫 + dst try/catch 兑底”完整修复 P0（熳断）缺陷**；流式写盘转记为需 SDK 契约变更的后续项（不阻塞 M1）。

### P0-3 内存水位线口径 / 阈值统一（解除恒拒）
- `plugin-manager.ts` 阈值常量 `DEFAULT_YELLOW_MB=300/DEFAULT_RED_MB=400`（L22-23）按聚合口径重标定为 yellow=1500 / red=2500（Electron 多进程工作集聚合的合理区间），并新增可配置项 `memory.yellowMB`/`memory.redMB`（加入 `settings-handlers.ts` 与 `plugin-sdk-host.ts` 白名单）。
- `memory-monitor.ts aggregateRssMB()`（L61-72）：保留全应用聚合作为"应用是否已承压"的展示/闸门语义，但 `executeOp` 的 OOM 硬闸门改为额外检查插件 Worker 进程 RSS，两者任一 red 即拒绝——即"聚合口径"与"Worker 口径"各司其职。
- **[修订·W1] Worker RSS 获取路径写死为同步方案**：`MemoryMonitor` 新增 `getWorkerRssMB(serviceName='luuk-plugin-worker'): number`，内部 `app.getAppMetrics().find(m => m.name === serviceName)?.memory?.workingSetSize / 1024`（找不到返回 0，视作未启动）——零额外 IPC，与 `aggregateRssMB` 同源 API。executeOp 闸门 = `aggregate ≥ red || workerRss ≥ workerRedMB`，`workerRedMB` 默认 500（R7 实测峰值上限）。
- 统一 `plugin-worker.ts memory.getStatus`（L100-116）与本进程/聚合口径，标注来源，避免同一概念两套计算。
- 补水位边界不变量测试（green/yellow/red 随新阈值）。

## M2 · 安全与权限正确性（P1）

### P1-4 edit.write 绕过路径守卫
- `plugin-sdk-host.ts editWrite`（L154-177）：调用 `assertWithinLibrary(String(p.sourcePath))`；`_edits` 输出根由 `libraryId` 反查 `rootPath` 后 join，忽略插件传入目录。`edits-service.createEdit` 二次校验输出路径在库根内。

### P1-5 activePluginId 并发串位
- **[修订·C1] 影响范围纠正**：不仅非 edit.write——当前 `plugin-worker.ts callMain`（L73）在**消息层**用 `currentPluginId()`（全局 activePluginId）填 `req.pluginId`；而 `plugin-sdk-host.ts handleCall`（L78）/`dispatch`（L110）一律读消息层 `req.pluginId`，从不读 `p.pluginId`。故 `edit.write`（worker-sdk.ts L135 虽将 pluginId 放入 params）的**权限校验与落库 pluginId 仍取自 activePluginId**。叠加 `JobRunner` 默认 `BATCH_SIZE=10`+`Promise.allSettled`，`hostProcess.rpc` 不串行化，P0-1 修复后并发 executeOp 会**确定发生**串位。
- `plugin-worker.ts`（L77-82）：删除全局 `activePluginId`/`currentPluginId()`；`createPluginSdk(pluginId,…)` 闭包持有自身 id，`callMain(method, params, pluginId)` 显式透传并写入消息层 `pluginId`；移除 worker-sdk.ts L135 参数层的冗余 pluginId。
- **[修订·S3]** `callMain` 改为模块私有（不导出），仅通过 `createPluginSdk` 闭包暴露；内部硬断言 `if (!pluginId) throw`。
- 测试必须覆盖“两插件 executeOp 交错各自调 edit.write”，断言落库 pluginId 与权限校验 pluginId 均正确。

### P2-12 createSession 绕过权限/校验（提前到 M2，属安全）
- `worker-sdk.ts createSession`（L56-72）：忽略外部传入 `modelPath`，仅接受主进程 `sdk.inference.resolveModel` 返回路径；`inference.run` 带 pluginId 复核 `inference` 权限位。

## M3 · 可恢复性（P1）

### P1-6 Worker 崩溃后 loadedInWorker 陈旧
- `plugin-manager.ts setEnabled`（L164-207）：`enabled=false` 无条件 `loadedInWorker.delete(pluginId)`；订阅 Worker exit（见 P1-11）→ `loadedInWorker.clear()` 并对启用中插件重新 `plugin.load`。

### P1-8 模型状态不持久 / verifyModel 误删
- `model-manager.ts verifyModel`（L60-87）：`info.sha256` 缺失/空 → 只校验存在性（可选 size）+ `logger.warn`，**不删文件**；比较统一 `String(info.sha256).toLowerCase()`；校验成功即 `markDownloaded(id)`。
- `plugin-loader.validateManifest`：补 `requires.models[].sha256` 格式（64 hex）断言。
- `plugin-manager.initialize()`：启动时对本库已注册模型做一次 `verifyModel` 回填 state，修复"重启后文件在盘却显示未下载"。

### P1-9 第二个作业永久 pending
- **[修订·C2] 前置依赖 1**：将 `MAX_CONCURRENT_JOBS` 从 `job-handlers.ts`（L11，IPC 层私有常量）下沉为 `JobRunner` 构造参数（默认 1），IPC 层改读 `runner.getMaxConcurrent()`，避免双源真值。
- **[修订·C2] 前置依赖 2**：`database.ts` 新增 `getPendingJobs(limit?: number): Job[]`，SQL 用 `WHERE state='pending' ORDER BY priority DESC, created_at ASC LIMIT ?`（现有 `getAllJobs()` 全表扫描不可接受）。
- `job-runner.ts executeJob` 收尾（L248-266）：作业转 done/cancelled 后，扫描 DB `state='pending'` 且 kind 已注册 handler 的作业，在 `runningJobs.size < MAX` 时按 priority 依次 `start()`（自泵）。
- **[修订·C2] 自泵触发点扩展**：除 `executeJob` 收尾外，`cancel()`（L140-150）与 `pause()`（L117-128）释放槽位后也需拉起——三处统一调 `private pump()`；否则用户取消队头作业后第二个仍永久 pending。

### P1-11 exit 监听跨实例污染 + 状态先于加载
- `plugin-host-process.ts doStart`（L99-124）：`const self=this.worker; self.on('exit', c=>{ if(this.worker===self) this.handleWorkerExit(c) })`；`shutdown()` 内 `self.removeAllListeners('exit')`。（[修订·W3] 函数签名在 L99，非 L103）
- **[修订·C3] setEnabled 回滚修正**：当前 `setEnabled(true)` 先 `enabledPlugins.add()`（L174）+`setState('activated')`（L175）再 `ensureStarted()`+`rpc('plugin.load')`。计划旧版“失败回滚 idle 并清 loadedInWorker”**漏了 `enabledPlugins.delete`**——会把两个成功标志位后置到 load 成功之后：`ensureStarted()+rpc('plugin.load')` 全部成功后才 `enabledPlugins.add(pluginId)` 与 `loader.setState('activated')`；任一失败→不动 enabledPlugins、回滚 state 到 `idle`、`loadedInWorker.delete(pluginId)`（当前先置 activated 会让未加载插件通过 `handleCall` 权限门）。

## M4 · 并发与资源（P1/P2）

### P1-7 SDK 超时/取消
- `plugin-worker.ts`（L53-75）：按方法分级超时——`sdk.edit.write`/`sdk.fs.read`/`sdk.fs.write` 用 60s（或按 payload 字节动态），其余 5s；超时后仍回收到 `sdkPending` 的响应做幂等丢弃。
- **[修订·W2] 删除“callId 幂等去重”条目**：当前 callMain 超时仅 reject **无任何重试逻辑**，worker-sdk 也不重试，幂等去重前提（重试）在本里程碑内不存在，属过度设计。保留“超时后 `handleSdkResponse` 幂等丢弃迟到响应”（当前已天然安全），文档注明“如未来引入自动重试再补幂等键”。
- **[降级·后续项] `plugin.cancel`(jobId/opId) 协作式逐瓦片取消**：原计划新增 Worker 侧 RPC 让插件在文件/tile 循环边界协作退出。经实施评审，这需要变更 SDK 取消令牌契约并横切 plugin-sdk-host/worker-sdk/各内置插件循环（4+ 模块），与 W4（逐带流式写盘）同类——属增强而非 M4 核心缺陷。**本里程碑以“分级/动态超时 + 迟到响应幂等丢弃”收尾 P1-7（Worker 卡死/长阻塞的可见缺陷）**；`JobRunner.pause/cancel` 已 abort 主进程 Promise 且 item 级 abort 阻止后续作业项拉起，当前作业项跑完即停止扩散。逐瓦片即时取消转记为需 SDK 取消令牌契约变更的后续项（不阻塞 M4）。

### P1-10 驱逐未接线 + acquire 双建竞态 + 无 LRU
- `plugin-manager.ts`：`memoryMonitor` `levelChange==='red'` → `hostProcess.rpc('memory.evict')`（`memory.evict` RPC 现注册但无调用方）。
- **[修订·S5] 订阅位置明确**：`this.memoryMonitor.on('levelChange', …)` 订阅写在 **PluginManager 构造函数**（而非 `initialize()`），避免 feature flag 关闭时永不订阅、重复初始化时重复订阅。
- `inference-pool.ts acquire`（L46-88）：加 `Map<string, Promise<Session>>` 创建锁，同名并发只建一个；加最大会话数 LRU（按 `lastUsedAt` 驱逐 `refCount===0`）；`residentMB` 用模型文件大小填充或删除该字段。
- `plugin.unload`：销毁该插件创建的会话。

## M5 · 算法质量与测试补盲（P2）
- **P2-13 upscale 量纲/倍率**：`buildTileTensor` 前对输出张量做 min/max 判 `[0,1]`/`[0,255]`（替代首像素 `f32[0]<=1.001`）；**[修订·S2] min/max 循环跳过非有限值（`if(!Number.isFinite(v)) continue`），全为非有限时抛业务错**，防 NaN 污染整图变黑；`assert realScale===scale` 否则报错或全程以 `realScale` 为准；解码统一 `.toColourspace('rgb')` 防灰度伪彩色；删 `srcC` 死代码。
- **P2-14 matting 绝对 alpha**：min-max 后叠加固定软阈值（默认 0.5）或改 `x*255` 保留绝对量纲；把后处理抽成可测纯函数。
- **P2-15 张量视图 byteOffset**：`matting asFloat32`（L101-116）按 `t.data` 视图 + `byteOffset`/`length` 构造，校验 `prod(dims)*字节数===byteLength`；`int64` 单独处理（对齐 `worker-sdk.deserializeTensors`）。
- **P2-16 契约漂移**：删除 `types/plugin.ts` `@deprecated WorkerRpcRequest` 中已移除的 `inference.*` 方法示例。
- **P2-17 前端可见性**：`ImageGrid` 菜单项按 `pluginStore.isOpVisible`（三条件）过滤或标注"需下载模型"。
- **P2-18 打包**：`build-builtins.mjs`/`prebuild` 断言 `dist-electron/plugins/builtins/*/index.js` 存在，缺失即失败（避免直接 `electron-builder` 静默无插件）；`models.directory` 改为运行期读取（当前仅构造时读一次）。
- **P2-19 测试**：为 matting/upscale 后处理、分块拼贴、量纲判定补单测；matting 单次解码（`normalize`+`decode` 合并）。

> **[已实施 2026-09-19·M5 落地说明]**
> - P2-13/14/15：后处理均抽为纯函数模块 `builtins/upscale/post.ts`、`builtins/matting/post.ts`（esbuild 随 index.ts 一并打包，不破插件产物）。upscale 量纲改为 `resolveQuantizeFactor` 全局 min/max（跳过非有限、全非有限抛错）+ 首块 `realScale===scale` 断言；matting 改绝对量纲 `saliencyPlaneToAlpha`（默认 softThreshold 0.5）；`asFloat32` 按 byteOffset 构造视图并处理 int64 + 尺寸校验；`image.decode` 统一 `.toColourspace('srgb')`。
> - P2-17：新增 `pluginStore.getOpAvailability`（区分隐藏 vs 置灰“需下载模型”），`FileContextMenu` 据此过滤/置灰；`isOpVisible` 重构为 `visible && !needsModel`。
> - P2-18：`build-builtins.mjs` 构建后 `verifyArtifacts()` 断言各 `<name>/index.js` 存在；`ModelManager` 支持传 `() => string` 运行期解析 `models.directory`。
> - P2-19 已补：upscale-post、matting-post、pluginStore(getOpAvailability) 共 29 例。
> - **降级项（不阻塞）**：“matting 单次解码合并”经评审：`normalize`（模型输入 320×320）与 `decode`（原尺寸合成）是两个不同目的、不同尺寸的 sharp 管线，合并会改变模型预处理语义（放大/插值核），属正确性敏感区，保留现状；如需去重可后续引入“一次读图 + 两路输出”的 SDK 方法（需契约变更）。
