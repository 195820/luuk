# Agent 架构派生规划（Phase 12 候选）

> **本文只定切入点与形态，不承诺排期。** 它是 [ai-crawler-direction-2026-q4.md](ai-crawler-direction-2026-q4.md)（Phase 9-11 AI/爬虫方向）的**衍生文档**：那份文档解决"AI 能力怎么落地成插件与作业"，本文解决"这些能力之上，能否再加一层会用工具的智能体，把人要点的几十次点击变成一句话"。
>
> **一句话定位**：Agent 不新增任何能力。它只是给已经存在的能力（搜索、标签、评分、相似图、AI 修图队列）装一个**听得懂人话的调度台**。
>
> **实施状态**：`draft` — 未开工。全部原料已存在且稳定（见 §2），因此每一级均可独立交付、独立验收、可单独放弃。

## 1. 为什么这个项目适合派生 Agent

三个前提条件恰好都已具备，这在同类桌面应用里并不常见：

| 前提 | 本项目现状 | 对 Agent 的意义 |
|---|---|---|
| **存在结构化意图 schema** | `SearchCriteria`（[src/types/index.ts](../../src/types/index.ts) `SearchCriteria` 定义处）字段封闭、类型明确 | 自然语言有一个**确定的翻译目标**，不必让 LLM 自由发挥 |
| **功能面已经 IPC 化且薄** | 7 个 handler 文件按域拆分，handler 基本是 service 单例的透传（[src/main/ipc/](../../src/main/ipc)） | 每个既有 IPC 通道就是一只**现成的工具**，Agent 工具层零改造 |
| **长任务有持久化车间** | JobRunner（[src/main/services/job-runner.ts](../../src/main/services/job-runner.ts)）支持优先级/暂停/取消/断点续跑，进度走 `jobs:subscribeProgress` 广播 | Agent 的"慢任务"有地方可扔，**不必在对话里干等几小时** |

反过来说：如果这三样不具备，Agent 就会退化成一个需要自己造队列、自己定义意图格式的独立子系统——那才是真的高成本。

同时它继承了 Phase 8 的一条已经付出过代价的经验：**权限与路径守卫必须在服务端集中**。[plugin-sdk-host.ts](../../src/main/plugins/plugin-sdk-host.ts) 的 `API_PERMISSION_MAP` + `assertWithinLibrary` 就是 Agent 工具权限表的直接模板，不必重新设计。

## 2. 模块意图 → Agent 能力映射

逐模块检视"这个模块当初被设计出来是想干什么"，据此判断它能派生出哪一层 Agent 能力：

| 现有模块 | 模块原始意图 | 派生的 Agent 能力 | 派生依据 |
|---|---|---|---|
| `SearchCriteria` + `searchImages` | 多维组合搜索 | **L1 查询编译器**：NL → criteria JSON | schema 封闭可校验，是天然的结构化输出目标 |
| 只读查询面：`getImagesByFolder` / `getAllTags` / `getLibraryStats` / `getHistory` / `getFavoriteImages` / `findSimilarImages` | 库元数据检索 | **L2 Agent 工具面**（只读档，无需确认） | handler 即 service 薄包装，包装成工具零改动 |
| 可逆写面：`tagImages` / `createTag` / `setFavoriteRating` / `batchRename` | 元数据编辑 | **L2 写工具** + 预览-确认 | 均可逆、均可重试；设计文档 Q7「AI 标签是否允许自动写入」未定案 → 默认必须用户采纳 |
| 危险写面：`deleteFiles` / `moveFiles` / `removeLibrary` | 文件操作 | **本期不注册为工具** | 回收站不支持恢复（roadmap #8），不可逆 |
| JobRunner `jobs:enqueue` / `jobs:list` / `jobs:pause` / `jobs:cancel` | 持久化后台作业 | **L3 异步作业编排**（入队即返回 jobId，不等待） | 数十小时级作业不可能在对话里同步完成（roadmap C1） |
| `plugins:execute` + op 可用性判定（[pluginStore](../../src/stores/pluginStore.ts)） | AI 处理入口（upscale/matting/autotone） | L3 流水线节点 | 批量流水线优先（Phase 8 设计 D4 决策）同构 |
| `media://` preview 档（1200px 懒生成） | 渐进式降采样出口 | **Vision 工具的图片供给源**（只发 preview，不发原图） | 硬约束 C4「上传原图不可接受」；与 cloud provider「默认关闭 + 强提示」同策略 |
| pHash / `SimilarImagesPanel` / 浏览历史 | 相似检测与行为数据 | 智能整理类**建议报告**（去重建议、相册建议、收藏推荐 #39） | 纯读分析 → 输出建议，零写风险 |
| `SiteAdapter` / 三级去重（Phase 9 未开工） | 数据采集 | 远期：自然语言 → 选择器规则包生成 | 依赖 Phase 9 开工，本文仅预留接合点 |

**关键观察**：与 Phase 8 设计文档 §11 同样的结论在这张表上重演——**没有一处是"重写"**，全部是"把已有接口换个调用方"。这是 Phase 1-7 把数据层与 IPC 层做扎实的直接收益。

## 3. 三级形态与实际用处

架构视角容易看不出价值，本节直接对照现有操作成本。

### L1 查询编译器 —— 省掉填表

**现状成本**：找一个「2025 年 8 月拍的、5 星、大于 4000 像素的 JPG」要在 [SearchPanel](../../src/components/SearchPanel.tsx) 里依次操作 5-6 个控件（关键词框、日期起止、标签多选、尺寸下限、格式勾选、评分）。

**派生后**：输入一句自然语言，Agent 翻译成 `SearchCriteria` 交给原搜索链路执行。

> 「找去年 8 月拍的海边照片，5 星的，要大于 4000 像素的 JPG」

- **单次 LLM 调用，无循环**，执行是确定性的
- 编译结果**回填到现有搜索面板的控件上**再执行——用户看得见它理解了什么，改了控件语义就一起生效，UI 零新概念
- 翻译错了顶多搜不出来，**不会损坏任何数据**，可无条件降级为普通搜索

**这是 ROI 最高的一级，因此排在最前。**

### L2 工具调用循环 —— 省掉重复点击与逐张筛选

**现状成本**：每个操作都要逐次手动做。给 43 张图打标签 = 多选 → 右键 → 选标签 → 确认；挑废片 = 一张张放大看 → 评分；查重复 = 手动开相似面板 → 对比 → 决定。面对 7000+ 张的库，这些是劝退量级。

**派生后**：Agent 持有工具面，自行决定调用顺序：

> 「把刚才搜出来这批海边照片打个'海边'标签，构图明显歪的单独列给我看」
> 「库里有没有重复的图？留评分最高的那张，其余列个清单」
> 「我的库里格式和尺寸分布什么样？哪些文件夹最占地方？」

写操作前必定弹出**预览确认卡**：「准备给这 43 张打'海边'标签 —— 确认 / 取消 / 修改范围」。**它提议，你拍板。**

### L3 异步作业编排 —— 省掉人工看守批处理

**现状成本**：AI 修图单张数秒到数十秒，批量几千张是**几小时**的事。当前流程只能：手动多选 → 右键 → 入队 → 干等；要调整得自己跑去 [JobProgressBar](../../src/components/JobProgressBar.tsx) 暂停取消。

**派生后**：Agent 成为流水线调度员，编排完扔进队列就走，进度仍走既有通道展示：

> 「把收藏里所有低于 1080p 的图排队做 4 倍超分」
> （几小时后）「昨晚那批跑得怎么样了？失败的是哪些原因？」
> 「失败那批重跑一遍，换质量优先参数」
> 「先找相似图里画质最差的一批 → 其余做智能评分 → 低于 3 分的打上'待删除'标签」

最后一例本来是三步手动 + 两次几小时等待，这里被编排成队列里的作业链。

### 三级对照

| 级别 | 替代的现状 | 一句话用处 | 风险量级 |
|---|---|---|---|
| **L1** | 搜索面板 6 个控件 | 省掉**填表** | ≈ 0（只读、可降级） |
| **L2** | 右键菜单 / 批量对话框逐个点 | 省掉**重复点击与逐张筛选** | 低（写操作必经确认） |
| **L3** | JobProgressBar 干等 | 省掉**人工看守几小时的批处理** | 低（走的还是既有队列与闸门） |

## 4. 架构决策记录

体例沿用 [ai-crawler-direction](ai-crawler-direction-2026-q4.md) §3：**决策 / 理由 / 被否决 / 失效条件**。

### A1 Agent 循环放主进程，纯新增模块

| 要素 | 内容 |
|---|---|
| **决策** | 新增 `src/main/agent/`，Agent 循环跑在主进程；不新建进程拓扑 |
| **理由** | LLM 调用是**网络 IO 而非 CPU 重负载**，不构成对 IPC / `media://` 流式响应的阻塞，因此不触碰性能红线（启动 <3s / 内存 <500MB / 滚动 ≥30FPS）。真正重的活（推理、批处理）已经下沉到 utilityProcess 与 JobRunner，Agent 只是在它们前面做编排 |
| **被否决** | ① 放 `utilityProcess`——重蹈 Phase 8 已踩过的 Worker 启动失败与崩溃熔断复杂度，换来的隔离收益为零 ② 做成 `kind:'agent-provider'` 插件——`PluginKind` 是封闭五元枚举，扩它等于扩类型面 + 加 RPC 链路；且 Agent 是**核心交互入口**，不该是可选能力（插件化承载的是"失效频率高的能力"，见 Phase 8 D3） |
| **失效条件** | 若未来 Agent 需要在本地侧做持续重计算（如本地 embedding 批量生成），那部分**必须另行下沉**，届时本决策仅覆盖"编排 + LLM 通信"这一层 |

### A2 LLM 通信零新依赖

| 要素 | 内容 |
|---|---|
| **决策** | Node 全局 `fetch` + OpenAI-compatible `/v1/chat/completions`（`tools` 字段）+ SSE 流式解析；Provider 基座 = 云 API（用户自配 baseURL / key）+ **Ollama 本地**（`http://127.0.0.1:11434`，同协议） |
| **理由** | OpenAI 兼容协议已成为事实标准，一家实现覆盖数十个后端；Ollama 兜底让「写真内容不出本机」成为可选路径，与 C4 的隐私要求对得上 |
| **被否决** | Vercel AI SDK / LangChain——与「插件与核心保持轻依赖」的既有哲学冲突，且它们解决的（多 provider 适配、流式抽象）恰好是本方案里最薄的一层 |
| **失效条件** | 若需接入的某个重要后端不兼容 OpenAI 协议，则在 `llm/` 下新增一个 provider 实现即可，不影响上层循环 |

### A3 工具直连 service 单例，权限分四档

| 要素 | 内容 |
|---|---|
| **决策** | 工具实现直接调用 `ImageService` / `MasterDB` / `JobRunner` / `PluginManager` 单例（与 IPC handler 同一入口），**不经 `ipcMain` 转发**；注册表按 `readonly` / `write-reversible` / `async-job` / `destructive` 四档标注，`destructive` 本期一律不注册 |
| **理由** | 与 handler 同入口 = 天然共享同一套参数契约与错误处理，不存在"Agent 能看到但 UI 看不到"的行为漂移；四档权限直接移植 `API_PERMISSION_MAP` 的成熟做法 |
| **被否决** | Agent 走 `electronAPI` / 直连 DB 与 fs——前者多一层无意义转发，后者绕过 `assertWithinLibrary` 与补偿式一致性，风险不可控 |
| **失效条件** | 若某能力只有 IPC handler 里有逻辑（而非 service 里），必须先把它抽到 service 再包装成工具，**不允许复制 handler 代码** |

### A4 上下文一律经检索收敛

| 要素 | 内容 |
|---|---|
| **决策** | 绝不向 LLM 全量投喂库元数据。所有检索走 `searchImages` / `getLibraryStats` 工具，单次返回 ≤200 条；会话历史按 token 预算截断，不常驻 |
| **理由** | 2026-09 那份设计文档对向量的结论是「明确否决全量常驻内存」；同理，百万张库的元数据直喂 LLM 既超成本也超上下文，且**用户搜不准时无法归因** |
| **被否决** | 「把整个库的清单丢给模型让它自己整理」——听起来聪明，实际不可行且不可控 |
| **失效条件** | 无。这是纪律 |

### A5 Feature flag 渐进 + 密钥不落盘

| 要素 | 内容 |
|---|---|
| **决策** | `agent.enabled` 默认 **false**，未开启时 UI 完全隐藏入口、模块不初始化；`agent.apiBase` / `agent.model` / `agent.visionEnabled` / `agent.confirmWrites` 进 [settings-service](../../src/main/services/settings-service.ts) 白名单，**API key 仅存进程内存**（每次启动在设置面板输入），不落 electron-store，日志脱敏 |
| **理由** | 沿用 `plugins.enabled` 的成功纪律：flag → Phase 末评估 → 达标默认开启 → 清理 flag。electron-store 是明文 JSON，密钥落盘等于写在桌面 |
| **被否决** | 密钥加密落盘（引入 keytar / safeStorage 依赖与平台差异）——本文阶段不值得 |
| **失效条件** | 若 Agent 转为默认开启功能，则密钥持久化需求真实出现，届时按 `safeStorage` 方案单独设计 |

## 6. 依赖关系与出口条件

```
阶段一  1 → 2 → 3 → 4 → 5 → 6          （5/6 可与 3 并行）
阶段二  7、8 依赖 1/2；9 依赖 7+8；10 依赖 9；11 依赖 10
阶段三  12、13 依赖 11；14 依赖外部 Phase 9（不在本文关键路径）
测试    15 随各阶段并行；16、17 收尾
```

| 阶段 | 出口条件 |
|---|---|
| 阶段一 | 20 条真实中文查询的编译结果**人工核对准确率达标**，且非法输出被校验层 100% 拦下（不执行） |
| 阶段二 | 只读问答闭环可用；**任何写操作未确认前不得落库**（须有测试用例覆盖「拒绝」分支） |
| 阶段三 | 至少一条模板链路走完并可在 JobProgressBar 观察/暂停/取消；Agent 入队的作业与手工入队行为完全一致（同闸门、同优先级语义） |

---

## 7. 风险与缓解

| 风险 | 缓解 |
|---|---|
| LLM 幻觉产出越权 criteria（如自行伪造 `favoritePaths`） | 校验层字段白名单；`favoritePaths` / `tagIds` 的解析一律服务端完成（`SearchCriteria` 定义处已注明「服务层填充，渲染层不传」） |
| 写工具误操作（批量打错标签 / 改错名） | 预览-确认为必经环节；只注册可逆操作；`deleteFiles` / `moveFiles` / `removeLibrary` 本期不注册 |
| API key 泄露 | 仅存进程内存，不落 electron-store；日志脱敏 |
| 大库上下文爆炸 | 工具返回分页 ≤200 条；「列出全库」类意图不直接执行，引导为「统计 + 抽样」 |
| 云 API 图像隐私 | L1/L2 **只传元数据不传图**；vision（14）默认关闭 + 仅 preview 档 + 强提示 |
| 与性能红线冲突 | 懒初始化（flag 关闭零开销）；LLM 网络 IO 不阻塞 IPC；会话不落盘、不常驻 |
| Agent 绕过 JobRunner 资源闸门 | 只经 `jobs:enqueue` 入队（含既有并发判断逻辑），Agent 不自建执行器 |
| 确认疲劳（用户无脑点确认） | 确认卡显示**影响条数与抽样缩略图**而非「确认执行吗」；大批量强制展示明细摘要 |

## 8. 已否决的替代方案

| 方案 | 否决理由 | 参见 |
|---|---|---|
| Agent 做成 `kind:'agent-provider'` 插件 | `PluginKind` 封闭枚举需扩类型面 + Worker RPC；Agent 是核心交互入口而非可选能力 | A1 |
| Agent 循环放 utilityProcess | LLM 为网络 IO 无隔离必要，反引入 Worker 启动失败/熔断复杂度 | A1 |
| 引入 Vercel AI SDK / LangChain | 与轻依赖哲学冲突，其抽象在本方案中是最薄一层 | A2 |
| ReAct 文本解析做工具调用 | 现代模型均有原生 function-calling，文本解析徒增不确定性 | A2 |
| Agent 直连 DB / fs | 绕过路径守卫与补偿一致性 | A3 |
| 全量库元数据喂 LLM 做「智能整理」 | 违反成本与上下文现实，且失败不可归因 | A4 |

## 9. 本期不做

- **爬虫规则生成 Agent**——等 Phase 9 爬虫方案定案与目标站点清单（Q1）确认
- **长时间无人值守的自主 Agent**——所有写操作必经确认
- **多 Agent 协作拓扑**——单循环足够；子任务下沉走 JobRunner 而不是「子 Agent」
- **语义搜索工具**——依赖 Phase 9 CLIP embedding 表落地
- **Agent 会话持久化 / 历史回溯 UI**——本期会话为内存态
