## 二、第一条线：稳定性与基建收尾（P0，约 2-3 天）

### 1. 修复 3 项遗留缺陷（源自 docs/defect-summary-2026-09-15.md）
- **R-1 搜索面板被 header 裁剪**：`src/components/SearchPanel.tsx` 展开内容改为 `createPortal` 到 body 的浮层（`fixed` 定位，跟随搜索框位置），不受 header `overflow:hidden` 裁剪；注意与 frameless 拖拽区（`-webkit-app-region`）的鼠标事件冲突
- **R-2 主题切换实时性复验**：`src/stores/themeStore.ts` 的 `setMode/setAccentColor/setDensity` 已同步调用 `applyTheme()`，疑似已修复；需实机验证浅色/密度/强调色切换即时生效，若仍有问题排查 `applyTheme` 写入 `document.documentElement` 的 class 与 CSS 变量是否覆盖 `SettingsPanel` 预览区
- **R-3 关闭应用卡顿**：`electron/main.ts:316-328` `window-all-closed` 中 `void shutdownApp()` 改法为 `shutdownApp().finally(() => app.quit())`；`SHUTDOWN_TIMEOUT_MS` 2s→1.5s 并为每一步（stop/kill ffmpeg/pluginManager/jobRunner/closeAllDatabases）加耗时日志定位瓶颈；排查 `scanner.ts`/`library-monitor.ts`/cache 过期定时器是否有未清理的 `setInterval`

### 2. 测试基建：解决 better-sqlite3 ABI 错配
- 69 个失败用例（`file-service/search/stats/tag/database-cascade/database-migration/job-runner`）因原生模块按 Electron ABI 147 编译而 vitest 走系统 Node 无法加载
- 方案 A（推荐）：`vitest.config.ts` 中为 DB 相关测试配置 `testEnvironmentOptions` + 将 better-sqlite3 替换为内存版 mock（`vi.mock`），把纯 SQL 逻辑与原生绑定解耦
- 方案 B：DB 相关回归改到 Electron 内跑（复用 `tests/playwright` 通道），vitest 只跑非 DB 用例并在 CI 报告中标注
- 验收：`npm run test:run` 全绿（或剩余失败项均有明确标注的 Electron 通道回归覆盖）

### 3. 仓库卫生

## 三、第二条线：Phase 8 补全（P1，约 5-7 天，依赖第一条线完成）

> 目标：把「框架骨架 + autotone 演示」变成设计文档第 14 节 Phase 8 出口条件所定义的完整交付。

### 5. `luuk.*` SDK 真实链路（缺口最大项）
- 新建 `src/main/plugins/plugin-sdk-host.ts`：主进程侧 SDK 实现（`luuk.library` 只读查询 / `luuk.fs` 受限读写复用 `file-service.ts` 路径校验 / `luuk.jobs` / `luuk.progress` / `luuk.log` / `luuk.settings`），权限比对 `plugin.json` 的 `permissions[]`，越权直接拒绝
- 新建 `src/main/plugins/worker-sdk.ts`：Worker 侧 `luuk.*` 代理，将 API 调用序列化为 RPC 请求发到主进程
- `electron/plugin-worker.ts` 接入 worker-sdk，替换当前 stub 分发；插件 entry 真实加载（`require(plugin.json.entry)`）替换模拟执行
- 对应设计文档：`ai-crawler-direction-2026-q4.md` §5.3/§5.4/§5.6

### 6. ONNX 推理链（含 PoC 前置）
- **PoC R1（先行，1 天内）**：`onnxruntime-node` 在 Electron 40 + Node 24 + `npmRebuild:false` 下的 `build:dir`/nsis 双通道打包验证，脚本放 `scripts/`（沿用 `bench-scan.mjs` 命名风格），实测结果回填设计文档附录 A。R1 失败则按预案降级（autotone 零模型链路仍可交付，matting/upscale 排期冻结）
- 新建 `src/main/plugins/inference-pool.ts`（Worker 侧）：会话池 `Map<modelId,{session,refCount,lastUsedAt}>`、并发上限=1、线程 `max(1,cores-2)`；`luuk.inference.createSession/run` 从 stub 换真实实现，与 `memory-monitor.ts` 三级水位线联动（>400MB 驱逐 + 暂停 JobRunner）
- ModelManager 补下载 IPC（`.part` 断点续传 + SHA256 校验，复用 `media://` Range 经验），入 `plugin-handlers.ts`

### 7. JobRunner 生产接线

## 七、已否决的备选方案

- **跳过 Phase 8 收尾直接开 CLIP 索引（Phase 9）**：否决——`plugin-sdk-host`/`inference-pool` 缺失时 CLIP 无处挂 `ai-index` kind，且 JobRunner 无生产入口，跳过会重演「三套后台任务各自为政」的反模式
- **先做单图交互式编辑器（EditViewer）**：否决——D4 决策明确批量流水线优先，编辑器 UI 工作量超过 Phase 5-7 总和，延后至 Phase 10
- **把 69 个失败测试直接 skip 了事**：否决——database-migration/job-runner 是 Phase 8 新增核心，必须通过 mock 解耦或 Electron 通道获得真实覆盖
- **WebGPU / transformers.js 进渲染进程**：否决——设计文档 §16.2 已归档该路线（违反 C3 红线，EP 实验性未发布）
- **立即实现 matting/upscale 再补 SDK**：否决——无 `luuk.*` SDK 的插件只能私有直连 onnxruntime，破坏 §5.4「宿主集中管控」这一全部内存治理成立的前提
